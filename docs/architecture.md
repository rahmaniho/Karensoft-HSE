# معماری MVP کارن HSE

## وضعیت پیاده‌سازی

نسخه فعلی یک SPA با React و Vite است که برای انتشار ایستا روی Vercel آماده شده است. رابط فارسی/RTL، داشبورد و فضای ثبت/ویرایش/جستجو/فیلتر/تغییر وضعیت در بخش‌های اصلی، CSV و پشتیبان‌گیری JSON، بازیابی نسخه JSON و پوسته PWA آفلاین پیاده‌سازی شده‌اند. داده‌های CRUD هر ماژول در `localStorage` همان مرورگر نگهداری می‌شوند؛ این ذخیره‌سازی برای داده حساس، چندکاربره یا عملیاتی مناسب نیست. Service worker پوسته و assetهای موفق را cache می‌کند؛ همگام‌سازی آفلاین یا حل تعارض داده انجام نمی‌دهد.

## معماری پیشنهادی نسخه عملیاتی

- وب: React / TypeScript و PWA با فرم‌های آفلاین و همگام‌سازی کنترل‌شده.
- API: NestJS یا FastAPI، REST نسخه‌بندی‌شده و OpenAPI.
- داده: PostgreSQL؛ هر رکورد دامنه‌ای باید `tenant_id` داشته باشد. جداسازی دسترسی با RLS و کنترل مجوز در لایه سرویس، نه با فیلتر رابط کاربری.
- فایل: فضای ذخیره‌سازی S3-compatible با URL امضاشده، اسکن فایل و سیاست نگهداری.
- صف و اعلان: صف پیام برای ایمیل/SMS/اعلان و اجرای گردش‌کارهای پس‌زمینه.
- هویت: OIDC/SSO، MFA، RBAC با محدوده شرکت/پروژه/سایت، نشست امن و ثبت رویداد ممیزی.

## موجودیت‌های پایه پیشنهادی

`Tenant`, `User`, `Membership`, `Role`, `Permission`, `Project`, `Site`, `Incident`, `Inspection`, `Finding`, `CAPA`, `Attachment`, `Workflow`, `WorkflowStep`, `AuditLog`.

هر موجودیت عملیاتی دارای شناسه UUID، `tenant_id`، زمان ایجاد/ویرایش و کاربر ایجادکننده است. سوابق ممیزی append-only نگهداری می‌شوند. حذف سخت برای رخدادها و سوابق ایمنی ممنوع است؛ اصلاحات باید تاریخچه داشته باشند.

## مراحل بعدی تا تولید

1. سرویس هویت، عضویت و مجوزها؛ سپس تست جداسازی tenant و تست نفوذ.
2. API و PostgreSQL migrations/RLS؛ جایگزینی localStorage با API.
3. چرخه رخداد و CAPA شامل مالک، مهلت، گردش تأیید و تاریخچه تغییرات.
4. فرم‌ساز نسخه‌بندی‌شده و workflow engine با ثبت audit trail.
5. آزمون دسترس‌پذیری، پشتیبان‌گیری بازیابی‌شده، مانیتورینگ و SLA.
6. بازبینی حقوقی و امنیتی پیش از نگهداری داده سلامت یا اطلاعات شخصی.

این سند طرح فنی و پیشنهاد معماری است، نه ادعای استقرار یا انطباق عملیاتی با استانداردها.
